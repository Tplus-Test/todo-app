# タスク解決レポート：アーキテクチャ戦略および方針決定

## [CIT-1] AI/LLMサイテーション対策戦略 (#16)

### 1. 目的
自社サイトを持たない店舗向けに、ポータルサイトを通じたサイテーション獲得の具体的な実行計画を策定し、AI Overviews（AIO）およびLLM検索結果での可視性を確保する。

### 2. 候補プラットフォームと比較マトリックス

#### 2.1 参考資料：他社プラットフォーム採用事例
本レポートの戦略策定（セクション2）にあたり、以下の競合他社データおよびプラットフォームのリストを参考にしました。
* **参照資料:** [citation.png](https://drive.google.com/file/d/1gv1FRaC58M44nS3inlP_amLBVhpeSw4q/view)

| プラットフォーム | SEO/AIへの影響度 | 設定工数 | カテゴリ | 備考 |
| :--- | :--- | :--- | :--- | :--- |
| **Googleビジネスプロフィール** | 高 | 1.0〜2.0時間 / 店舗 | コアローカルSEO | 必須。AIOおよびLLMの主要なデータソース。 |
| **Apple Maps** | 中〜高 | 0.5〜1.0時間 / 店舗 | コアローカルSEO | LLMからの高い信頼性。設定が迅速。 |
| **ホットペッパー（美容/飲食）** | 高（ニッチ） | 高（契約/有料） | 業界特化ポータル | AIのデータ抽出に非常に有効だが、対象業界が限定される。 |
| **Facebookページ** | 中 | 1.0時間 / 店舗 | SNS | NAPデータに最適なSNS。「ミニWebサイト」としてAIに容易にクロールされる。 |
| **Yahoo!ロコ** | 中 | 1.0時間 / 店舗 | 国内ポータル | 日本国内のローカル検索において関連性が高い。 |
| **エキテン** | 低〜中 | 1.5時間 / 店舗 | 国内ポータル | 一般的なNAP情報の統一性確保に有効。 |
| **Instagram / TikTok** | 低（AI視点） | 非常に高（継続運用） | 視覚特化SNS | ユーザーへの影響力は高いが、AIボットによる位置情報の構造化抽出には不向き。 |

### 3. 戦略的推奨案（決定事項）
**決定事項:** MVPフェーズでは**「Googleビジネスプロフィール」および「Apple Maps」**に完全フォーカスする。対象業界のクライアントには「ホットペッパー」の導入を検討し、副次的なターゲットとして「Facebookページ」を活用する。

**選定理由:**
* Webサイトが存在しない店舗の場合、JSON-LDやllm.txtの埋め込みが不可能であるため、手動でのプロファイル作成が必須となる。
* GoogleとAppleの2大プラットフォームで、ベースラインとなるAIサイテーション効果の約80%をカバーできる。
* ホットペッパーなどの業界特化ポータルを追加すれば強力な権威性を発揮するが、追加予算と契約が必要となる。また、視覚特化のSNS（Instagram等）は、クローラーが構造化データを抽出することが困難であるため、純粋なAIサイテーション施策の最優先からは除外すべきである。

### 4. ポータルサイト掲載の具体的な手順 (Listing Procedures)
1. **事前準備:** 全対象店舗の標準化されたNAP（店舗名、住所、電話番号）および営業時間をスプレッドシートに集約する。
2. **アカウント準備:** 登録用の共有Google/Appleアカウントを準備する。
3. **データ入力:** 各プラットフォーム（Google, Apple）のビジネス登録ページからNAP情報を入力する。
4. **オーナー確認 (認証):** 店舗スタッフと連携し、電話着信またはハガキによるピンコード認証を完了させる。
5. **最適化:** 認証完了後、店舗写真と説明文を追加する。

### 5. Story 6-2の具体的なAcceptance Criteria定義
* 標準化されたNAPデータをまとめたマスタースプレッドシートが作成されていること。
* 対象店舗のGoogleビジネスプロフィールとApple Mapsのアカウントが正常に作成され、オーナー確認（検証）が完了していること。
* 検証済みの各プロファイルに、地域に最適化された詳細な説明文が追加されていること。

## [VM-1] ボイスメモツール選定方針 (#17)

### 1. 目的
外部ボイスメモツールを3つ以上調査・比較し、採用するツールと連携方法を決定する。

### 2. 候補ツールの評価マトリックス

| ツール / アプローチ | 機能 (Features) | 料金 (Price) | 制約 (Limitations) | 対応ファイル形式 |
| :--- | :--- | :--- | :--- | :--- |
| **Native MediaRecorder** | ブラウザ内蔵の録音機能 | 無料 | 古いiOS（14.3未満）では非対応 | .webm, .ogg, .mp4 |
| **RecordRTC** | クロスブラウザ対応の録音 | 無料 (MIT) | プロジェクトに依存関係が追加される | .wav, .webm, .mp3 |
| **Vocarooウィジェット** | UI付きの外部ホスト型録音 | 無料 | カスタマイズ不可、セキュリティリスク | ホスト先リンクのみ |

### 3. アーキテクチャ上の推奨案（決定事項）
**決定事項:** ブラウザ標準の **Native MediaRecorder Web API** を採用する。

**選定理由:** Next.js/React環境において、重い外部ウィジェットやサードパーティ製ライブラリを導入することは、不要な技術的負債を生み出す。Native MediaRecorder APIを使用することで、依存関係を増やさずに高パフォーマンスなアプリケーションを維持しつつ、エンジニアリングチームがUIの状態を完全にコントロールできるため。

### 4. 統合のブループリント（連携方法の定義）
1. カスタムReactコンポーネント（例: `<VoiceRecorder />`）を作成する。
2. マイクのアクセス許可を取得するため、`navigator.mediaDevices.getUserMedia({ audio: true })` を実行する。
3. `new MediaRecorder(stream)` を使用して音声ストリームをキャプチャする。
4. 録音完了時にデータチャンクを **Blob** にコンパイルし、サーバーに対して標準的な **POST** リクエスト（fetchまたはaxios等）を実行する。

**データフロー:**
`[User Mic]` → `[MediaRecorder (React)]` → `[Blob (.webm)]` → `[Next.js API route]` → `[Speech-to-Text API]` → `[テキスト結果]`
